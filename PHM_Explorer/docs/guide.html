Getting your PHM result into the Explorer

Two steps: export a fitted phm2 object to JSON from R, then load that file into the interactive dendrogram & ΔPmc heatmap. This page covers both, and exactly what the exporter needs from your fit.

Open the Explorer → no installation of the app itself — it runs in the browser

01

Install

The Explorer itself is a self-contained web page — there's nothing to install for it. What you need on the R side is the PHM package (to produce a fit) and jsonlite (to write the export). Both come from the usual places:

# once per machine
install.packages("jsonlite")
install.packages("remotes")         # if you don't already have it
remotes::install_github("aturfah/PHM")

Then grab export_phm_json.R — the exporter script — and keep it next to your analysis. It has no dependencies beyond PHM and jsonlite, both loaded internally with library().

02

Export a result

Fit as usual with PHMv2(), then hand the result to export_phm_json(). It always exports the full-fidelity tree — every fitted component as a leaf, every merge — the Explorer collapses that down to fewer leaves for display, live, in the browser. You never re-export just to change the display threshold.

library(PHM)
source("export_phm_json.R")

fit <- PHMv2(X, ...)   # your existing fit, X is 2D here

export_phm_json(
  fit,
  X        = X,                                # optional — adds the scatter panel
  out_path = "my_result_export.json",
  label    = "two moons benchmark, n = 1000"
)
ⓘ Only phm2 is required. Everything else — the scatter panel, per-point shading, the footer label — is optional and simply doesn't render if you leave it out.

This also works on a pooled or ensemble fit (for example, a paramsList assembled across bootstrap replicates) — nothing in the exporter assumes a single mclust object exists.

When the fit isn't already 2D

X and the scatter panel's layout are two different jobs, and the exporter keeps them separate. X is only ever used to compute posterior probabilities — it has to match the fit's own dimensionality, whatever that is. What actually gets plotted is a separate argument, xy: any n×2 layout of your choosing. If you don't pass xy, the first two columns of X (X[, 1:2]) are plotted; for a 2D fit that is the fitted space itself, which is why the example above never needed to mention it. Once your original data has more than two dimensions, the first two columns are usually a poor view, so hand the exporter a real embedding — a UMAP or t-SNE projection, a couple of principal components, anything two-dimensional — instead:

# X is the full original-space data the fit was built on (any dimension)
fit <- PHMv2(X, ...)

# a 2D layout computed separately, purely for the scatter panel
embedding <- umap::umap(X)$layout

export_phm_json(
  fit,
  X        = X,          # drives the posterior shading — full dimensionality
  xy       = embedding,  # drives what's actually plotted — any 2D layout
  out_path = "my_result_export.json"
)

If you don't have the original data at all — say you only kept someone else's posterior probabilities — pass those as z directly alongside xy; X isn't needed in that case.

03

Exporter arguments

The full signature is export_phm_json(phm2, X = NULL, xy = NULL, z = NULL, out_path = "phm_export.json", label = NULL, digits = 4, prob_eps = 0.005).

ArgumentRequiredWhat it does
phm2 yes Your PHMv2() result. Only phm2$paramsList is assumed to exist — a single fit or a pooled/ensemble list both work.
X optional Original-space data the fit was built on, matrix or data frame, column count matching the fit's own dimensionality. Used only to compute posterior probabilities when z isn't supplied — never plotted directly unless it also happens to be what you pass as xy.
xy optional n×2 coordinates for the scatter panel — what's actually drawn on screen. Any 2D layout: a UMAP/t-SNE embedding, a PCA projection, or the fit's own two dimensions. If omitted and X is given, the first two columns of X (X[, 1:2]) are used.
annotation optional A length-n factor or character vector of categories, one per row of the layout. Adds a second, static scatter panel with one color per category. Display-only: the fit and the posterior shading never see it. NA shows as “unlabeled”. Row i must be the same observation as row i of X; the exporter errors if the lengths differ. Exports without it are unchanged.
z optional An n×K posterior-probability matrix. If X is given (matching the fit's dimensionality) and z isn't, it's computed for you — a Gaussian-mixture posterior via Cholesky log-density and softmax — straight from phm2$paramsList, so this works even with no mclust object at all. Pass this directly when you already have posteriors from elsewhere; X is then optional.
out_path optional Where to write the JSON. Default "phm_export.json".
label optional A short free-text description of the run (e.g. "compound benchmark, n=11700, seed=202"), shown in the Explorer's footer.
digits optional Rounding applied to point coordinates and merge heights. Default 4.
prob_eps optional Posterior probabilities at or below this are dropped from the (sparse) export. Default 0.005 — keeps the file small even with hundreds of fitted components, since posteriors are typically concentrated on a handful per point.

The resulting file carries meta (K, merge criterion, n, label), the authoritative leaf order, the merge tree (leaves + internal merges with their d*-scaled heights), and — whenever a layout and a source of posteriors were both available — the plotted coordinates and their sparse posterior weights. Tile colors for the heatmap aren't precomputed; the Explorer derives them live from each merge's height, so recoloring at a different display threshold needs no second export.

04

Load it in

Open the Explorer, then use the controls in the header:

load a PHM export… → choose your .json file or drag & drop the .json file anywhere on the page show top N of K components → collapse finer merges for display

Either loading method accepts anything export_phm_json() produced, and both go through the same validation (a clear alert if the file isn't a PHM Explorer export, instead of a silent failure). Loading a new file fully replaces whatever was showing — scatter panel, threshold range, and footer label all update to match. The threshold control never needs a re-export: raising or lowering it re-collapses the same full-fidelity tree client-side, absorbing the chronologically finest merges first, exactly as if PHMv2 had been asked for that many components from the start.

ⓘ Nothing on this page assumes ground-truth labels — every color and shading comes from the fit itself. The one exception is an optional annotation you export yourself, shown in its own static panel and never used by the fit.
05

Reading the display

Hover a leaf tick or a merge branch in the dendrogram to inspect it. The whole subtree beneath your cursor highlights together, down to every leaf it contains, and three other panels answer in sync:

GoldThe hovered branch — in the tree, and the points it claims in the scatter panel, shaded by posterior probability.
GrayEverything not currently hovered. Scatter points stay faintly visible at rest, never fully transparent.
Blue heatmap cellThat pair of components merges late — well separated, distinguishable.
Red heatmap cellThat pair merges early — weakly distinguishable at the fitted resolution.

The heatmap sits directly beneath the dendrogram, column-for-column aligned with the leaf above it, so a branch and its corresponding block of the ΔPmc matrix read as one figure. The branch detail panel below both fills in the numbers for whatever you're hovering: which components it groups, the d*-scaled merge height, and — with a scatter panel loaded — how many points fall inside it.

06

Notes & troubleshooting

"That file doesn't look like a PHM Explorer export" — the loader checks for meta, nodes, and xlabOrder at the top level of the JSON. This means the file wasn't produced by export_phm_json(), or was edited afterward and lost one of those keys.

No scatter panel showing — it only appears when the export includes both points and z, which needs a 2D layout (xy, or X[, 1:2] when xy is omitted) and a source of posteriors (z, or X in the fit's native dimensionality). A tree-only export is entirely valid; it just has nothing to shade.

"X has N column(s) but the fit has M dimension(s)" — X has to match whatever PHMv2() was actually fit on; it's never truncated to 2 columns for you. If your fit is higher-dimensional, pass the full X as-is and hand the exporter a separate 2D xy for the layout (see above).

Large fits stay fast — per-point posteriors are stored sparsely (prob_eps), and heatmap colors are computed from merge heights rather than stored as a full K×K matrix, so exports scale gracefully into the thousands of points and dozens of components.

Everything above the threshold line is derived once per export and reused for any display resolution — if you only want a different number of components shown, reach for the show top … of K control before you reach for R.
